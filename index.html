Diferenciais tecnicos

Mostra o encanamento em vez de vender magia.

O valor do Parrot PHP esta na simplicidade controlada: fluxo facil de seguir, contratos padrao de mercado, autenticacao com validacao explicita e uma base que nao esconde custo operacional atras de convencoes extensas.

O framework foi desenhado para entregar uma base REST moderna sem carregar o peso de um full stack. Em vez de empilhar abstrações proprietarias, ele usa PSR-7, PSR-15 e container padrao para que a leitura do request ate a resposta continue curta, objetiva e depuravel.

Essa escolha aparece em tudo: roteamento via FastRoute, DI em config/container.php, ORM via Eloquent fora do Laravel, JWT proprio em HS256 e respostas JSON padronizadas por Response e Resource.

O resultado nao e um experimento minimalista sem protecao. A base atual ja traz blacklist persistente de logout, CSRF ajustado ao uso de cookie, protecao contra IDOR, headers de seguranca, rate limit por usuario autenticado e suite integrada com banco real.

PSR

Contratos reconheciveis

PSR-4 no autoload, PSR-7 nas mensagens HTTP, PSR-15 na pipeline e container padrao para DI.

JWT

Validacao sem caixa-preta

DB

Eloquent como base ativa

Controllers, models e camada HTTP usam Eloquent. SQL raw fica restrito a seed e infraestrutura de testes.

QA

Teste contra banco real

A suite roda em APP_ENV=testing com MySQL, recria tabelas a cada teste e nao reintroduz SQLite.

Arquitetura atual

Um pipeline curto o bastante para caber na cabeca.

O fluxo principal implementado hoje segue uma ordem direta: entrada unica, aplicacao, middlewares, roteamento, controller, model ou resource e resposta JSON. Isso favorece leitura rapida, debugging simples e evolucao gradual das camadas.

01

Bootstrap

Registra fallback de excecao, carrega Composer, monta o container e inicializa o DatabaseCapsule.

02

Application

Cria a request a partir das superglobais, carrega middlewares globais e envia a resposta final.

03

MiddlewareQueue

Executa a pipeline no formato onion, permitindo interceptacao antes e depois do proximo passo.

04

FastRouteRouter

Registra metodos e caminhos, injeta atributos dinamicos e resolve middlewares de rota.

05

Invoker

Instancia o controller via container e injeta a request no metodo final sem acoplamento manual.

06

Controllers

Executam validacao, autorizacao e orquestram UserModel, TokenRevogado e resources.

07

JSON

Response e Resource padronizam itens, colecoes, mensagens e erros em um contrato consistente.

Seguranca implementada

Cookie seguro, blacklist persistente e controle de acesso real.

O escopo e enxuto, mas a base nao e permissiva. O codigo atual combina autenticacao manual, revogacao persistida, rate limit sensivel ao usuario autenticado, CORS com whitelist, CSRF para escritas autenticadas e protecao contra IDOR em regras de dominio.

JWT

Token entregue no cookie token

HttpOnly, SameSite=Strict, Path=/ e Secure quando a conexao e HTTPS, producao ou proxy confiavel sinaliza X-Forwarded-Proto=https.

Blacklist

Logout com revogacao persistida

TokenRevogado grava o jti em tokens_revogados, usa cache configuravel e ainda mantem cache local por processo.

Rate limit

Prioriza o sub do JWT valido

Usuarios autenticados sao identificados pelo token; sem JWT valido, o fallback e IP. O login usa alias proprio com 5 tentativas por 900 segundos.

CORS + CSRF

Defesa alinhada ao uso de cookie

CORS responde preflight e limita origens conhecidas. CSRF bloqueia escritas autenticadas que chegam de origem fora da whitelist.

Headers

Camada de hardening por padrao

nosniff, DENY, Referrer-Policy, Content-Security-Policy, Permissions-Policy, no-store e HSTS quando aplicavel.

Autorizacao

Admin nao vira default silencioso

UserController diferencia admin de usuario comum, valida id positivo e impede IDOR ao exigir titularidade quando cabivel.

Ordem real dos middlewares globais

  • ErrorHandlerMiddleware
  • SecurityHeadersMiddleware
  • RateLimitMiddleware
  • CorsMiddleware
  • CsrfGuardMiddleware

Regras de acesso ja implementadas

  • GET /api/usuarios e exclusivo de admin.
  • Usuario comum so acessa, altera ou remove o proprio recurso.
  • Email e senha exigem senha_atual na atualizacao.
  • Usuarios criados pela API entram sempre como tipo=user.

API implementada hoje

Um dominio pequeno, mas ja operavel.

O repositório atual entrega autenticacao, endpoint /me, CRUD de usuarios com soft delete, paginação, revogacao de token e respostas JSON padronizadas. O foco esta em ter uma base segura e previsivel para evoluir.

Autenticacao

  • POST /api/auth/login rate_limit_login
    Autentica por email e senha, gera JWT e devolve o usuario com o cookie token.
  • POST /api/auth/logout JwtAuthMiddleware
    Revoga o token atual, limpa o cookie e remove expirados da blacklist.
  • GET /api/auth/me JwtAuthMiddleware
    Retorna os dados do usuario autenticado a partir do payload ja validado.

Usuarios

  • GET /api/usuarios somente admin
    Lista usuarios com page padrao 1 e limit padrao 20, maximo 100.
  • GET /api/usuarios/{id}
    Admin acessa qualquer usuario; usuario comum so acessa o proprio registro.
  • POST /api/usuarios somente admin
    Cria novo usuario comum. O campo tipo nao e promovido pelo cliente.
  • PUT /api/usuarios/{id}
    Atualiza nome, email e senha, descartando campos fora da whitelist.
  • DELETE /api/usuarios/{id}
    Aplica soft delete em deletado_em com a mesma regra de acesso por titularidade ou admin.

Instalacao e ambiente

Abre rapido, sobe rapido, testa com o banco certo.

O setup minimo do projeto e direto: clonar, instalar dependencias, rodar migrations, popular o admin inicial e subir o servidor embutido do PHP ou o Caddy do proprio repositório.

Bootstrap local

Instalacao, migrations, seed e execucao.

setup.sh 
git clone https://github.com/arthur-oliveira-oficial/parrot-php.git
cd parrot-php
composer install
database.sh 
php database/scripts/migrate.php
php database/scripts/seed.php
serve.sh 
php -S localhost:8000 -t public

Producao e operacao

Comportamento mais rigido quando sai da bancada.

Em producao, o Parrot PHP fica menos tolerante com configuracoes improvisadas. O processo deve receber variaveis do ambiente, Redis passa a ser obrigatorio e a configuracao de proxy e HTTPS deixa de ser detalhe.

ENV

Sem carregar .env automaticamente

public/index.php nao le o arquivo quando APP_ENV=production. O ambiente precisa chegar pronto ao processo.

REDIS

Cache distribuido deixa de ser opcao

CACHE_STORE=redis e a configuracao minima recomendada para sustentar rate limit e blacklist distribuidos.

EDGE

Proxy confiavel precisa ser declarado

TRUSTED_PROXY_IPS controla quando X-Forwarded-For e X-Forwarded-Proto podem ser confiados.

Checklist minimo de operacao

  • Definir JWT_SECRET forte.
  • Publicar apenas origens conhecidas em CORS_ALLOWED_ORIGINS.
  • Configurar APP_URL corretamente.
  • Manter HTTPS e Redis disponiveis.

Defaults reais do rate limit

  • Global: 60 requisicoes por 60 segundos.
  • Login: 5 tentativas por 900 segundos.
  • Resposta inclui Retry-After e cabecalhos X-RateLimit-*.
  • OPTIONS fica fora da contagem.

Testes e garantias

Integracao de verdade, sem maquiar o banco.

A suite automatizada cobre autenticacao, CRUD, cache, restricoes de producao, confianca em proxy reverso e protecoes de origem. O pressuposto e claro: testar com MySQL real, criar o banco se necessario e reconstruir tabelas a cada caso.

Banco

MySQL em parrot_test

Ciclo

Schema recriado a cada teste

tests/TestCase.php cria o banco se necessario, executa migrations e roda os seeds em toda execucao.

Escopo atual

Base segura para crescer, sem fingir que ja e uma plataforma.

O Parrot PHP entrega hoje um nucleo funcional e seguro para API JSON. O que ainda nao existe tambem faz parte da proposta: o projeto escolhe escopo enxuto para manter previsibilidade e clareza de evolucao.

Fora do escopo atual

  • Sistema de modulos ou plugins do framework.
  • Refresh token e autenticacao principal via Authorization: Bearer.
  • Filas, eventos de dominio ou scheduler.
  • Documentacao OpenAPI gerada automaticamente.
  • Camada administrativa pronta.
  • Abstracao de CLI propria alem dos scripts de banco.

O que ja sustenta a proposta

  • Fluxo HTTP simples de seguir.
  • Uso de PSR em vez de contratos proprietarios.
  • JWT proprio com validacao explicita.
  • Autenticacao por cookie HttpOnly.
  • Blacklist persistente de logout.
  • Producao com cache distribuido obrigatorio.
  • Testes integrados com banco real.
